1. 背景

这不是一个功能清单，而是一段业务描述。我们故意没有把需求写清楚，因为真实工作中需求也从来不会是清楚的。你需要自己理解这个业务、决定要做什么、决定不做什么。

我们是一家教育机构。目前有 10 名 admin（课程顾问 / 教务），每人手上大约跟进 100 名学生。有 20 名老师，每周固定开 60 节课左右。

一个学生的完整生命周期大致是：家长或学生来咨询 → 安排一节试听课 → 决定报名并购买课时 → 被排进每周的固定班级 → 每周上课、老师记录出勤和课堂反馈 → 课时快用完时续费，或者流失。

现在这些全靠 Excel 和微信群在管，经常出问题：学生被排进了时间冲突的两个班、试听完没人跟进、课时用完了才发现没提醒续费、老师不知道今天班里谁是新来的。

我们想要一个系统，从咨询试听开始，把这些学生好好管起来。

以上就是你能拿到的全部需求。其余一切——谁能看什么、班级怎么定义、课时怎么扣、冲突怎么算、admin 之间的学生能不能互相看——都需要你自己做判断。

2. 你要交付什么

开始前先 git init、设为 public 并把链接发给我们（见常见问题）。两部分，缺一不可。只有文档没有代码，或只有代码没有文档，都视为未完成。

Part A · 设计文档（放在仓库的 DESIGN.md）

不超过 3 页（草图不计）。我们想看到你怎么思考，不是排版。至少包含：

  1. 你对这个业务的理解：有哪些角色、各自关心什么、核心流程是什么。用你自己的话写，不要复述背景。
  2. 你决定要解决的问题和不解决的问题：这个系统第一版应该先做什么？为什么？哪些你认为重要但这次故意不做？
  3. 数据模型：实体、关系、关键字段。ER 图或表格都可以。特别说明：学生和 admin 的关系、班级和课的关系、课时是怎么记录和扣减的。
  4. 关键规则：至少列出 5 条你认为系统必须强制执行的业务规则（比如排课冲突、课时不足、试听只能一次……），并说明在哪一层执行。
  5. 你的假设和问题：背景里没说清楚、你自己做了假设的地方；以及如果能问业务方，你最想问的 5 个问题。
  6. 页面与信息结构：这个系统有哪些页面、每个角色登录后第一眼看到什么、最常做的操作离入口有几步。至少给出核心页面的草图——手绘拍照、Excalidraw、Figma、甚至 ASCII 都可以，我们看的是你怎么组织信息，不是画得好不好。
  7. Part B 的选择理由：你为什么选这个切片来做。

可以把这份文档当成你交给产品和设计同事的东西：读完它，他们应该知道要做什么、为什么、长什么样。

Part B · 一个能跑的垂直切片

从你的设计里选一条完整的流程，从数据库到界面做通。比如（只是例子，不要被限制）：

  • 咨询 → 安排试听 → 试听后标记结果并跟进
  • 把一个已报名学生排进每周班级，并正确处理时间冲突和课时
  • 老师视角：今天要上的课、每个班的名单、记出勤并扣课时
  • admin 视角：我手上哪些学生试听完没跟进、哪些快要用完课时

要求：

  • 真实的数据库、真实的后端、真实的前端，有登录和至少一层权限（比如 admin 可以查看所有学生，但只能修改自己的学生）
  • 你在 DESIGN.md 里列出的规则，凡是这条流程涉及的，必须在服务端强制执行，展示时我们会绕过界面直接测
  • seed 脚本生成足够的数据，让这条流程能被演示（不需要真的 1000 个学生，但要能看出"一个 admin 管很多学生"的感觉）
  • 基本的 loading / 空 / 错误状态
  • 一处用到 LLM 的地方，由你决定放在哪里最有价值。要求 structured output、服务端校验、失败时有合理降级。反例：为了用而用的"AI 聊天框"。

把这当作一次 hackathon：时间是固定的，范围由你控制。切片做窄一点、做透，好过做宽但每处都是半成品。

3. 技术要求

  • 技术栈不限，用你最顺手的。用 React + TypeScript 会更好，因为这是我们的日常技术栈；用别的也可以，展示时我们会多问一些 React 相关的问题
  • 后端语言、框架、ORM 不限
  • 推荐关系型数据库，平台自选（Neon / Supabase / 本地 Docker / SQLite 都行），README 写清楚怎么跑起来
  • LLM 自备，任何 provider 或本地模型均可，调用量很小，免费额度足够。key 不要提交到仓库
  • 尽量部署并在 README 附上链接，让我们展示前就能自己点一点。Vercel、Netlify、Render、Cloudflare Pages / Workers 都有长期免费档，对这个作业都够用。实在没时间可以跳过，本地能跑起来即可
  • 系统业务时间统一按 Australia/Melbourne 时区处理并展示，无需实现多时区切换

4. 我们怎么评估

思考质量 > 切片是否做对做透 > 代码你能解释清楚 > 界面设计是否清晰合理 > 技术栈匹配度

看什么好的表现不好的表现
理解业务识别出背景里没明说但显然存在的东西（比如家长和学生不是同一个人、试听和正式课的区别、课时是钱）把背景复述一遍，或者直接套一个通用 CRUD 模板
取舍明确说"第一版不做 X，因为 Y"，并且 X 确实是可以后做的什么都想做，或者砍掉的恰好是最核心的
数据模型能应对"一个学生同时在两个班""课时怎么退"这类追问只有几张表，字段没想过为什么存在
规则执行规则在服务端，绕过前端也拦得住；知道哪些用数据库约束、哪些用业务逻辑只在前端禁用了按钮
切片质量选的流程完整、能演示、边界情况有处理做了五个页面，每个都只能看不能操作
界面设计页面数量克制，每个角色打开就能看到自己最关心的信息；状态一眼能区分把每张表做成一个 CRUD 页面，用户要自己拼凑信息
AI 的使用放在真正省人力的地方，失败了系统照常工作为了有 AI 而加了个聊天框

5. 关于使用 AI 编程工具

我们鼓励使用 Claude Code、Codex、Cursor 等工具写代码，也可以用它们帮你梳理需求。

但 DESIGN.md 里的判断必须是你自己的，代码的每一行你都需要能解释。展示时我们会追问"为什么"，AI 生成的方案如果你答不上来为什么，比不做更糟。

  • 保留完整 git 历史，不要 squash
  • README 里写一段：AI 工具用在了哪些环节、有没有哪些 AI 给的建议你没采纳以及为什么

6. 展示环节（约 45 分钟）

环节内容
讲设计（10 分钟）你怎么理解这个业务、为什么这样建模、页面为什么这样组织、为什么选这个切片。不要念文档，讲你的思路
追问（10 分钟）我们会给一些你没考虑到的情况，看你怎么改。比如：一个学生转给另一个 admin 了怎么办？老师临时请假一周怎么办？
Demo + 破坏测试（10 分钟）走一遍切片；然后我们会尝试绕过界面违反你的规则
Code walkthrough（10 分钟）随机挑几处代码问为什么这样写、改成 X 会怎样
AI 工具（5 分钟）怎么用的、git log、对 MCP / Skills 的理解

7. 常见问题

需求这么模糊，我该怎么开始？先把背景读三遍，把所有名词列出来，想清楚它们之间的关系，再决定先做什么。这个过程本身就是作业的一部分。
可以问你们问题吗？可以。但不保证回答——有些问题我们故意留白。问不到答案的地方，自己做假设写进 DESIGN.md，比等待要好。
可以用组件库 / 脚手架 / 模板吗？可以。我们看的是你的判断和实现，不是从零手写 UI。
做不完怎么办？DESIGN.md 先保证完整，切片可以做得更窄。展示时说明你砍了什么、为什么，这本身就是我们想听的。
需要一直做满 24 小时吗？不需要，也不希望你这样。我们的要求是：从 git init 到最后一个 commit 不超过 10 小时。准备好开始时，第一件事就是 git init、把仓库设为 public、把链接发邮件给我们；之后什么时候做、怎么安排休息都由你决定。我们会看首次和末次 commit 的时间，这是为了让大家在同样的时间预算下比较，不是为了制造压力。
