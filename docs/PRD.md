# PRD · Austin Education 学生管理系统（预付费履约系统）

> 作者：许清楚（产品经理） · Phase 1 调研产出
> 状态：调研结论，供架构师/设计师/后端作为输入
> 定性与 R1–R8 业务事实由项目总监与用户共同锁定，本文件只做验证与补强，不推翻

---

## 0. 一句话定性

**这不是学生 CRUD，是一套预付费履约系统。**

课时同时是三样东西：**家长已经付出去的钱**（机构对家庭的负债）、**机构可销售的库存**、**对老师的排期承诺**。系统里所有东西都围绕"课时怎么来的、怎么没的"建模。谁把这条主线做成 CRUD，谁就答错了题。

这也是对评分表"不好的表现"里两条的直接规避：不复述背景（我们把背景翻译成"预付费履约"这个模型），不套通用 CRUD 模板（CRUD 无法表达"余额 = sum(ledger)"这种不可变账本语义）。

## 1. 问题陈述

### 谁、在什么场景、遇到什么痛点

| 角色 | 规模 | 现在的做法 | 现在为什么会坏 |
|------|------|-----------|----------------|
| admin（课程顾问兼教务） | 10 人，每人约 100 名学生 | Excel 名单 + 微信群 + 个人记忆 | 100 个学生 × 每周状态变化，靠记忆必漏。漏的不是数据，是**动作**：该打的跟进电话没打、该谈的续费没谈 |
| teacher | 20 人，每周共约 60 节 | 课前看群消息/问教务 | 不知道今天班里谁是新来的（没准备）、不知道谁请假了（白等）、出勤记在纸上事后补 |
| student / 家长 | 约 1000（学生与家长共用凭证） | 微信问顾问"还剩几节" | 课时减少没有可追溯的解释，"少了就是少了"，信任成本极高 |

### 现状为什么不行

作业原文点名了四个故障：**排进时间冲突的两个班 / 试听完没人跟进 / 课时用完才发现没提醒续费 / 老师不知道今天谁是新来的**。

这四个故障的共同点：**都不是"数据没存下来"，而是"没有人在正确的时刻被要求做正确的事"。** Excel 能存下 1000 个学生，但它不会在任何时刻催任何人。所以这个产品的第一性问题不是"怎么管理学生数据"，而是**"怎么把该发生但没发生的动作，变成系统里一个跑不掉的任务"**。

竞品侧独立佐证：行业分析普遍指出 DIY 表单 + 表格 + 单独预订工具的拼凑方案"在 50–150 名活跃学生之间就会崩"。Austin Education 在 1000 名量级，早已越过崩点。

## 2. 目标用户与 JTBD

### 画像 A：admin（课程顾问兼教务）— 主用户

- 10 人，每人 100 名学生，同时承担"卖课"和"排课"两种职责（这两个职责天然冲突：卖课要乐观，排课要严谨）
- 技术水平：熟练 Excel 与微信，不抗拒新系统但没时间学
- 每天实际工作时间被上课时段切碎

JTBD（按恐惧排序）：

1. **"当我手上有家长试听完还没回复时，我希望系统在我忘记之前就把他放到我面前，这样这单不会因为我忙而丢掉。"** → R2 / 待跟进队列
2. **"当我手上有学生课时快用完时，我希望提前被点名，这样我能主动谈续费，而不是等家长自己消失。"** → R6 / 低课时预警队列
3. **"当我把一个学生排进班时，我希望系统当场告诉我时间冲突/班满了/余额是 0，而不是等下周家长投诉。"** → R3
4. **"我不希望同事误改我的学生，但我也不希望完全看不到机构里发生了什么。"** → R7 的非对称读/写

**关键产品判断：admin 的首屏不应该是学生列表，应该是两个队列。** 学生列表是"我要找某个学生时用的"，队列是"我不知道今天该干什么时用的"。100 个学生的管理负荷下，后者才是每天打开系统的理由。

### 画像 B：teacher — 履约入口

- 20 人，人均每周约 3 节课。对这个系统极度低频、极度短时：一次使用 30 秒到 2 分钟
- 不关心机构经营，只关心"我这节课怎么上得顺利"

JTBD：

1. **"上课前 30 秒我要知道：今天班里有谁是新来的、谁请假了、谁只剩最后一节课了。"**
2. **"下课后我要在 30 秒内点完出勤，不要让我填表。"**
3. **"学生请假我不想背锅——系统已经替他预填了状态，我只在实际有出入时覆盖，并且我覆盖的动作要留痕。"** → 请假由学生端发起 + 老师覆盖写 Ledger

**关键产品判断：老师是系统里最弱也最关键的入口。** 老师的一次出勤提交 = 一次扣钱。所以提交动作必须（a）足够快，否则老师会拖到课后批量补录，数据失真；（b）不可抵赖，因为它是账务凭证。这两条同时成立的唯一办法是：默认状态由系统预填，老师只做例外覆盖。

### 画像 C：student / 家长（家庭账号，学生与家长共用同一凭证）

- 约 1000 家庭。guardians 表只存联系人信息、无凭证——即"家长不单独登录，用孩子的账号看"
- 技术水平：手机为主，微信习惯
- 与系统的交互频率：低（每周看一次课表、每学期谈一次续费），但**每一次交互都是高情绪的**（涉及钱）

JTBD：

1. **"我要随时能看到还剩几节课，以及每一节是怎么没的。"** → R5 对外可见
2. **"我要能自己请假，并且在按下请假之前就知道这节课扣不扣。"** → R4 规则前置可见
3. **"我不想为了问余额去发微信等回复。"**

**关键产品判断：对家长展示的不应该是"余额 = 4"这个数字，而是"余额 = 4，因为这 8 条流水"。**

依据不是产品直觉，是法律现实：中国司法实践对预付式消费明确认定——**消费记录通常由经营者控制，经营者无正当理由拒不提交的，法院可根据消费者主张认定事实**。即：一旦发生退费争议，谁拿不出完整流水谁败诉。所以 append-only ledger（R5）在家长侧的可见性，是**举证能力**，不是 UI 装饰。反面证据同样存在：主流平台被投诉"到期后拒绝提供历史数据""导出数据要另收约 500 美元、不交就丢失 5 年数据"。

### 3.2 替代方案（2）

| 替代方案 | 定位 | 为什么会被选 | 为什么不够 |
|----------|------|--------------|-----------|
| **Excel + 微信群**（当前现状，100% 份额） | 零成本、零学习成本的现状解 | 这是我们要替换的**真正对手**。它不花钱、没人需要培训、改起来随心所欲。任何新系统如果让 admin 每天多花 10 分钟维护数据，就会被悄悄放弃，回到 Excel | 不会在任何时刻催任何人。故障清单（冲突/漏跟进/漏续费/老师不知新生）全都源于此。行业共识：拼凑方案在 50–150 活跃学生处崩 |
| **通用 CRM（HubSpot / Notion / Airtable）+ Calendly** | 通用销售管道 + 通用预约 | 免费档够用，团队可能已经在用 | 语言不通：它说 deals / pipelines / contacts，教务说学生 / 班 / 出勤 / 课时。**与课堂数据天然断开，必须维护两套系统**。为销售团队设计，不是为教务设计——它不知道"这个人这周上了几节课、还剩几节" |

### 3.3 从差评里读出的三条市场空白

1. **转化漏斗的起点没被建模。** 主流平台管的是"已在读的学生"，试听要么不存在，要么只是一节普通课。行业评论直言：线索管理"直到你已经因为跟进太慢丢掉一批试听学生之后，才会意识到它有多重要"。这正是 R1 + R2 的位置。
2. **课时与排班被切成两个模块。** 排课系统做冲突检测，账务系统做余额，没有人把"余额 > 0"作为排班的前置校验。竞品的排课冲突检测只做"时间/容量"，不做"库存"。这正是 R3 的差异化部分。
3. **AI 一旦进关键路径，坏了就是灾难。** 大量差评指向"客服全是 AI 模板回复""自动化不工作，对方也不知道什么时候修"。这正是 R8 的设计前提：**系统动作不依赖 LLM**。

## 4. 我们的差异化

1. **把"课时"建模成不可变账本，而不是一个可变字段。** 竞品存余额，我们存流水。余额是 sum 出来的副产品。这既是账务正确性，也是法律举证能力。
2. **把"跟进"和"续费"建模成任务队列，而不是报表。** 竞品给老板做 dashboard（看得到），我们给 admin 做队列（做得掉）。看得到不等于会被处理。
3. **把"试听"作为一等公民实体。** 有独立生命周期、有 48h SLA、有且只有一次（R1）。竞品里它只是个联系人标签。
4. **排班校验同时管时间、容量、余额三个维度。** 因为课时是库存，不是记账结果。
5. **LLM 只输出建议，永远不进入扣费路径。** 决策卡是给人看的，不是给机器执行的。

### MVP 范围（P0）

#1–#8，Effort 合计 **11.0 小时**。略超预算，故第 9 节给出切片内的取舍建议。

### Part B 切片推荐（重要：作业只要求一条完整链路）

**切片 = "试听 → 成交开账 → 排班 → 上课出勤扣课时 → 低课时预警 → LLM 续费决策卡"**，即课时从进来到出去的完整生命周期。

选它的四个理由：

1. **它覆盖 8 条规则里的 8 条。** R1/R2 在试听端，R3 在排班端，R4 在出勤端，R5 贯穿全程，R6 在预警端，R7 在登录与写隔离，R8 在续费卡。没有其他切片能做到这一点。
2. **它端到端证明了核心洞察。** 钱进来（开账）→ 钱出去（出勤扣）→ 钱快没了（预警）→ 钱再来（续费卡）。评委只要跟着走一遍，就理解了"课时是钱"。
3. **LLM 放这里最自然。** 低课时是自动触发的事件，admin 此刻最需要的是"这个人该不该续、该怎么谈"的判断辅助，而不是一个聊天框。省的是人力和判断成本。
4. **演示 3 分钟讲完一个故事**，符合"讲设计 10 分钟 + Demo 10 分钟"的节奏。

**降级方案（时间不够时，按此顺序砍）**：先砍试听端前端页面（保留 R1/R2 的服务端规则 + seed 数据，用 admin 队列演示），省 1.5h；再砍 LLM 转化决策卡（保留续费卡这一处 LLM，作业只要求一处），省 1.0h。砍到 8.5h 仍是一条完整可演示的链路。

## 6. 明确不做清单（每条带原因）

| 不做 | 原因 |
|------|------|
| **支付网关集成** | 作业不要求，且是 demo 陷阱：需要商户号、webhook、对账，任何一环失败都会让演示崩掉。"成交开账"用 admin 手工登记收款即可，Ledger 语义不变。真做时它是独立模块，插在 CreditPackage 之前 |
| **经营报表 dashboard** | 评分表明确批评"把每张表做成一个 CRUD 页面，用户要自己拼凑信息"。dashboard 是给校长看的，而作业场景里没人扮演校长。做了就是堆功能，且会稀释"admin 队列"这个真正的主张 |
| **邮件 / SMS 外部通知** | 需要第三方账号与送达配置，10 小时预算内不稳定。系统内队列已能证明"不漏"的机制；外部通知是同一份队列的分发渠道，是纯增量，可后做 |
| **补课 / 调课 / 顺延** | 这是 R4 的例外分支，业务规则高度依赖机构政策（补课券？无限顺延？限期补？）。**但必须在 DESIGN.md 里写出处理方式**，因为评委明确会追问"老师临时请假一周怎么办"。不做 ≠ 不回答 |
| **老师可用性管理 / 可视化排班台** | 排班的难点是校验，不是拖拽。把 Effort 花在 R3 的服务端校验上（绕过前端也拦得住）比花在日历 UI 上性价比高一个量级 |
| **家长微信小程序 / 原生 App** | 交付物是网页端。家长端做响应式网页即可覆盖"随时看余额"这个 JTBD |
| **多校区** | 背景未提及。校管家"多校区"被评"操作复杂"，说明它是复杂度炸弹而非卖点 |
| **1 对 1 私课差异化建模** | 背景描述的是周期性班组。Jackrabbit 的教训是"为班组设计的系统做私课很笨重"——我们反过来，先把班组做透 |
| **学生转 admin 归属变更的 UI** | 归属变更是低频 + 高争议操作。**但 owner_admin_id 的变更历史必须在数据设计里预留**（追问点："一个学生转给另一个 admin 了怎么办"）。UI 不做，模型要能答 |
| **课时包有效期 / 冻结** | 法律上它是退费争议焦点之一，但当前锁定事实里没有。**建议 CreditPackage 预留 expires_at 字段但 MVP 不强制校验**，并在 DESIGN.md 假设章节写明。理由：留字段是 5 分钟成本，后加是迁移成本 |

## 7. R1–R8 反向验证（对照竞品差评逐条判定）

| 规则 | 判定 | 依据 | 需要处理的问题 |
|------|------|------|----------------|
| **R1** 同一学生同一科目只能试听一次 | **真痛点，但严格度需确认** | 竞品侧：主流平台根本没有"试听"这个一等实体（Jackrabbit 只有联系人式的 Lead File），转化漏斗缺失被行业评论点名为最大空白。我们把它建出来，方向正确 | "同一科目"的粒度存疑：现实中家长常要求换老师再听一次。**建议保留为服务端硬规则，但提供 admin 显式豁免 + 留痕出口**。硬规则 + 可审计的例外，比一刀切或完全放开都好 |
| **R2** 试听结束 48h 内必须有跟进记录，否则进待办 | **真痛点，强验证** | 竞品侧最大空白区。行业评论原话：线索管理"直到你因为跟进太慢丢掉一批试听学生之后才会意识到它重要" | 48h 这个数字是我方假设，无可查行业基准。**真痛点是"必须有人负责"这个机制，不是 48 还是 24。** 见第 9 节 Q2 |
| **R3** 排班校验时段重叠 / 容量 / 余额 > 0 | **基线部分（时间、容量）+ 差异化部分（余额）** | 时间冲突检测是中国教培 SaaS 的标配卖点（多家宣称准确率 100%），属**行业基线，不做会被扣分**。余额 > 0 是差异化：竞品把课时与排班切成两个模块，没人把库存作为排班前置校验 | 无。这条最扎实。注意：只做服务端校验，不做可视化日历（见不做清单） |
| **R4** 出勤/迟到/旷课扣 1；提前 ≥24h 请假不扣 | **真痛点，强验证，且是差异化** | 行业实践明确定义课时状态集：attended / cancelled in time / late cancellation / no-show / rescheduled，由机构的取消政策决定是否计费。这正是 leave_approved vs leave_late。24h 阈值是行业惯例 | 学生端发起 + 老师覆盖 + 覆盖写 Ledger 留痕，这三件套解决了"老师怕背锅"这个真实心理障碍——比规则本身更重要 |
| **R5** Ledger 只增不改，余额 = sum(amount) | **最强验证，但证据来自法律而非软件差评** | 预付式消费司法解释：消费记录由经营者控制，无正当理由拒不提交的，法院可按消费者主张认定事实。反面证据：校宝被投诉"到期后拒绝提供历史数据"、主流平台被指"导出另收约 500 美元、不交就丢 5 年数据" | **必须把 R5 的产出对家长可见**，否则它只是一句技术洁癖。流水页而非余额数字，是这条规则的产品化落点 |
| **R6** 余额 ≤ 4 进预警队列，余额 = 0 不允许排课 | **真痛点，但形态需修正** | "课时用完了才发现没提醒续费"是作业原文点名的四个故障之一。竞品有"package 自动续订""retention analytics"，但都是**给老板看的图表**，不是给 admin 做的任务 | 阈值 4 是我方假设（按每周 1 节 ≈ 剩 1 个月推得）。**且"图表"必须改成"可被处理掉的任务"**，否则等于没做。见第 9 节 Q6 |
| **R7** admin 可读全量、只能写 owner_admin_id = 自己的学生 | **部分验证，属于组织假设** | 竞品侧证据薄弱：权限是标配（TutorCruncher 有自定义角色），但"读全量 + 写自己"这个**非对称**模型来自我们对 10 个顾问既竞争又协作的判断。侧面佐证：Teachworks 被指"多老师场景需要小心处理排班与出勤记录的归属权" | **这条是最需要业务方确认的。** 如果顾问之间是纯竞争关系，读也应该隔离；如果是纯协作，写也该开放。我们选的是中间态，理由是"机构需要全量视图做调度，但要防止误改与抢单"。见第 9 节 Q4 |
| **R8** LLM 输出枚举白名单校验，失败降级 ai_status: unavailable，系统动作不依赖 LLM | **真痛点，强验证，且是竞品教训的直接反面** | 大量差评指向 AI 进入关键路径后失效："客服全是 AI 模板回复""自动化不工作，对方也不知道什么时候修""推送没人要的功能、更新一塌糊涂"。R8 正是对这条教训的直接回应 | 无。**但要注意展示口径**：评委看的是"失败时系统照常工作"，所以 demo 里必须**主动演示一次 LLM 失败降级**，而不是只演示成功路径 |

### 我们漏掉的三条（建议补入 DESIGN.md，不一定进 MVP）

| 候选 | 来源 | 建议 |
|------|------|------|
| **R9 课时包有效期 / 冻结** | 法律判例：课程有效期是退费争议焦点 | CreditPackage 预留 expires_at 字段，MVP 不强制校验，但 DESIGN.md 写明假设 |
| **R10 老师请假 / 机构停课 → 该周课时如何处理** | 作业追问点明会问"老师临时请假一周怎么办"；也是老师侧强痛点 | MVP 不实现，但**必须在 DESIGN.md 里给出明确答案**（建议：退回学生账上，不扣，写一条 +1 的冲正流水而非删除原流水——这正好复用 R5） |
| **R11 学生归属变更留痕** | 作业追问点明会问"一个学生转给另一个 admin 了怎么办" | MVP 不做 UI，但 owner_admin_id 变更需记入 Ledger 式的历史流（理由同 R5：归属争议 = 业绩争议，一样要能举证） |

## 8. 验收标准（Given / When / Then）

### 核心链路

- **AC-1（R7 读隔离）** Given 我以 admin A 登录，When 我查看 admin B 的学生 S 的详情，Then 我能看到完整信息，但所有写操作入口不可见；且当我绕过界面直接调用写接口时，服务端返回 403 且不产生任何 Ledger 变更。
- **AC-2（R1 试听唯一）** Given 学生 S 已在数学科目完成一次试听，When admin 再次为 S 在数学科目创建试听，Then 服务端拒绝并返回已存在的试听记录 ID；不产生新记录。
- **AC-3（R2 48h SLA）** Given 学生 S 的试听在 T 时刻结束，When 到达 T+48h 仍无跟进记录，Then S 出现在负责 admin 的待跟进队列顶部，并标注超时时长。
- **AC-4（R3 时段冲突）** Given 学生 S 已在周一 16:00–17:00 的班级中，When admin 把 S 排入周一 16:30–17:30 的另一个班，Then 服务端拒绝，返回冲突班级名称与重叠时间段。
- **AC-5（R3 容量）** Given 班级 C 容量 8 且已满，When admin 再加入一名学生，Then 服务端拒绝并返回当前人数/容量。
- **AC-6（R3 余额）** Given 学生 S 余额为 0，When admin 把 S 排入任意班级，Then 服务端拒绝（R6 联动）；余额为 1 时允许排班，且排班成功后余额不变（扣费发生在出勤，不在排班）。
- **AC-7（R4 出勤扣费）** Given 一节已排定的课，When 老师提交状态为 present / late / absent，Then 服务端写入一条 amount = -1 的 Ledger，余额减 1，且该流水不可修改。
- **AC-8（R4 请假豁免）** Given 学生在上课前 25 小时提交请假，When 老师查看该课名单，Then 该生状态预填为 leave_approved；老师提交后**不产生扣费流水**，余额不变。
- **AC-9（R4 迟到请假）** Given 学生在上课前 23 小时提交请假，When 老师查看该课名单，Then 该生状态预填为 leave_late；提交后写入 amount = -1 的流水。
- **AC-10（R4 覆盖留痕）** Given 系统预填 leave_approved，When 老师覆盖为 absent，Then 写入 amount = -1 的流水，且流水记录 `overridden_by` = 该老师 ID 与原预填值。
- **AC-11（R5 只增不改）** Given 任意一条已写入的 Ledger，When 任何角色尝试 UPDATE 或 DELETE（含直接操作数据库），Then 数据库层拒绝（无 UPDATE/DELETE 权限或触发器拦截）。
- **AC-12（R6 预警）** Given 学生 S 余额变为 4，When admin 打开首页，Then S 出现在低课时队列，并按余额升序排列；当余额变为 0，S 仍在队列且标注"已耗尽、不可排课"。
- **AC-13（R8 LLM 降级）** Given LLM 服务不可用或返回不在枚举白名单内的值，When admin 打开续费决策卡，Then 卡片区域显示 `ai_status: unavailable` 的降级态，**但仍展示学生的余额、上课频次、最近出勤等事实数据**，且"标记为已跟进 / 创建续费任务"等动作照常可用。

### 边界条件

- 空状态：admin 首次登录两个队列均为空 → 显示"当前没有待跟进 / 低课时学生"而非空白表格；老师当天无课 → 显示今日无课而非空白课表；家长端无流水 → 显示"尚未购买课时包"并给出联系顾问的入口。
- 错误状态：所有 4xx 返回结构化错误码与**人话**原因（不显示 "invalid request"）；LLM 超时 ≥ 3s 即降级，不让 admin 等待。
- 加载状态：队列与课表使用骨架屏；出勤提交按钮进入 pending 并禁用，防重复提交（重复提交会导致重复扣费，这是最严重的边界 bug）。
- 边界值：余额 = 1 时排班允许、出勤后变 0 且不再允许排班；请假时间恰好等于 24h（判定为不扣，取 ≥）；跨夏令时的周一时段（Australia/Melbourne 有 DST，但时区固定不转换，需明确存储为本地时间 + weekday + 时分，不存 UTC）。
- 并发：两名 admin 同时把最后一个名额排给不同学生 → 服务端用唯一索引/乐观锁保证只有一个成功，另一个返回"容量已满"。
- 离线：老师端在弱网下提交出勤失败 → 明确提示未提交成功且按钮恢复可点，**绝不在本地静默缓存后重放**（会重复扣费）。
- 权限拒绝：teacher 尝试查看非自己班级的学生 → 403 且不泄露该生是否存在（防探测）。

## 9. 非功能需求

| 类别 | 要求 | 优先级 |
|------|------|--------|
| 性能 | 首屏 < 3s；API p95 < 500ms；出勤提交接口 < 300ms（老师在课堂上等不起） | P0 |
| 一致性 | 扣课时必须是幂等的：同一 lesson_id + student_id 只产生一条流水（唯一索引强制） | P0 |
| 安全 | HTTPS、JWT、所有写接口做 R7 归属校验、输入校验、登录速率限制 | P0 |
| 可审计 | Ledger 与归属变更不可删改；所有覆盖动作记录操作者与原值 | P0（本项目升为 P0，理由见 R5 法律论据） |
| 兼容性 | Chrome / Safari / Firefox 最新两版；老师端需适配平板与手机竖屏（课堂场景） | P0 |
| 时区 | 全部按 Australia/Melbourne 处理、不转换；时段存本地 weekday + 时分，不存 UTC | P0 |
| 图标方案 | 统一描边 SVG 图标库（具体选型由架构师按项目锁定，全项目一套不混用），尺寸 16 / 20 / 24px。**禁止 emoji 作为功能图标**。文档与 UI 文案中用文字描述图标，例如"铃铛图标""时钟图标""账本图标""警示三角图标" | P0 |
| 视觉 | 禁止紫色→粉色渐变主视觉（Indigo→Pink 渐变 + 发光边框 + 毛玻璃的组合禁用）。采用深蓝/石板蓝为主色的专业克制风格（参照 B2B SaaS 行业基线：极简瑞士风 / 数据密集风），警示态用琥珀色而非荧光色 | P0 |
| 文案 | 禁止占位式空洞文案（Lorem ipsum / Welcome to 之类）。所有空状态、错误提示写真实人话 | P0 |
| 可访问性 | WCAG 2.1 AA 基本合规（键盘可达 + 对比度 ≥ 4.5:1） | P2 |
| 国际化 | 界面简体中文（用户为澳洲华人家庭）；不预留 i18n（无海外用户） | P2 |

### 数据埋点方案

MVP 必须埋点（不埋 = 上线后无法验证"队列真的减少了漏跟进"这个核心假设）：

| 类别 | 事件 | 说明 |
|------|------|------|
| 激活 | `trial_created`, `followup_created`, `package_created` | 链路是否真的在跑 |
| 核心 | `attendance_submitted`（属性：status、是否覆盖预填、耗时） | 老师是否真的在课后 30 秒内完成 |
| 核心 | `low_credit_task_resolved` | 预警队列是否被处理掉——这是产品的价值主张 |
| 留存 | `session_start`, `queue_viewed` | admin 是否每天都来看队列 |
| 转化 | `renewal_created` | 续费决策卡是否真的带来续费 |
| 异常 | `error_occurred`, `llm_fallback_triggered` | R8 降级率，用于判断 LLM 是否值得保留 |

实现：`trackEvent()` 轻量封装；命名 `{对象}_{动作}`；每事件附 `user_id`、`role`、`timestamp`、`version`；**不采集 IP、不存原始输入内容**（涉及未成年人数据）。

## 10. 我最想问业务方的 5 个问题

1. **试听"一次"的粒度是什么？** 按学生 × 科目，还是学生 × 科目 × 老师？家长要求换个老师再听一次，算不算违规？（这条决定 R1 的严格程度，也决定要不要做豁免出口）
2. **48 小时怎么算？** 从试听下课时刻起算，还是从下一个工作日起算？跨公共假期 / 学期假怎么处理？另外，"跟进记录"的最低内容要求是什么——打过电话但没接，算不算跟进过？（R2 会不会变成一个被随便填掉的假指标，取决于此）
3. **课时包有没有有效期？退费怎么算？** 买 100 送 10 的赠送课时，退费时与正价课时同价吗？（这是法律争议高发区，也决定 CreditPackage 要不要 expires_at 与 amount_kind 字段。留字段是 5 分钟成本，后加是迁移成本）
4. **10 个 admin 之间是竞争还是协作？** 互相能看到对方学生的课时余额和跟进记录吗？学生转归属是单方操作，还是需要双方确认？（这直接决定 R7 的非对称模型对不对。我们当前选的是"可读全量、只写自己"）
5. **老师临时请假一周、或机构停课，那一周的课时怎么处理？** 退回到学生账上、顺延、还是照扣？这决定要不要在 R4 之外建一套冲正机制。（这也是评委明确会追问的点，答不上来比不做更糟）

**附加问题（第 6 个，但对数据模型影响最大）**：每周这 60 节课是**整个学期固定的周期性课表**，还是每周由教务重新排？如果固定，Class / Session 的建模应按"周期规则 + 例外"设计；如果每周重排，应按独立 Session 设计。两者的数据模型差别很大，我在 PRD 里按"周期性班组"假设建模。
